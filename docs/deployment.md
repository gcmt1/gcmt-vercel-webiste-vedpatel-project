# Deployment and recovery

**Release blocked, November 23, 2026.** The previously inspected public frontend bundle contained the legacy external payment service and COD code. The candidate uses a different checkout and schema. No migration, gateway registration, credential change or production deployment was performed. Record owner sign-off privately for the following gates.

## Establish the deployment map

Obtain the current production alias, immutable deployment ID, exact repository, branch and commit from the hosting administrator. Match the served asset and domain to that deployment. Identify the external checkout service, its return handler, any enabled Supabase Edge Functions, database projects, merchant accounts, writers, scheduled jobs and inbound callbacks. Record who owns each integration and which orders are still in flight. A GitHub deployment label or a string in a bundle cannot establish current routing or database privileges by itself.

## Rehearse in staging

1. Use a distinct hosting project, Supabase project, bucket, test identities, merchant sandbox and HTTPS site origin. Use synthetic records and a sanitized schema export. Verify the environment targets before opening forms. The known commercial hostname guard covers only its configured hostname. Never set production branch metadata manually to make a preview pass.
2. Obtain an owner-approved database backup, prove that it restores to an isolated instance, and record restore time, point-in-time recovery coverage and the identities allowed to restore. Keep the prior immutable application deployment and configuration revisions available.
3. Obtain the merchant integration kit and signed-off sandbox cases. Establish permitted order reference length/charset, encryption and encoding, merchant identifier presence, currency and amount scale, status and tracking fields, cancellation semantics, callback content type and exact public POST URL. Run success, decline, abort, duplicate, late and conflicting evidence, lost response, blocked return, interrupted browser, merchant inquiry and provider outage. Verify merchant-side transaction evidence against stored receipts and cart changes. Synthetic self-encryption proves only local agreement.
4. Run the compatibility review below before either migration. Both migrations are transactions; applying them is a separate authorized operation. The empty-project bootstrap is for a fresh isolated Supabase installation with auth and storage already installed. It is unsuitable for overlaying an existing merchant database.
5. Confirm business policies for COD eligibility and staff collection, stock reservation, delivery fees, discounts, taxes, invoice contents, returns/refunds and archival. Exercise historic COD and online orders, including guests, missing snapshot fields, mixed-case statuses and legacy identifiers. Verify signup confirmation, anonymous conversion, recovery links, images and exports through hosted service APIs.
6. The checked-in hosting policy allows the live gateway form destination. The loopback browser fixture substitutes the intercepted sandbox origin. Obtain approval for a staging-specific form policy and verify the actual response headers and form submission on that host. Run the checks in the README. Run the environment gate using the intended staging configuration. Establish and test an authenticated inquiry transport or a staffed merchant reconciliation procedure. Measure expected callback counts, latency, pending age and unresolved conflicts. Retain an operator contact and a procedure for customers reporting a debit on an unresolved order.

## Schema compatibility record

| Inspect before application | Required comparison and acceptance |
| --- | --- |
| Tables and column types | Compare every field used by the checkout and order functions with the live schema export. Check UUID versus sequence-generated IDs and sequence privileges, nullable profiles, text versus enum statuses, JSON versus text snapshots, numeric precision, timestamps and shipping columns. Test read/write compatibility using sanitized representative rows. |
| Cart, variants and catalog | Enumerate duplicate owner/product rows, pre-existing unique constraints/indexes, missing product references, empty size, null quantities, numeric stock and invalid discounts. The October migration needs unique owner/product pairs. The November migration replaces its named index with owner/product/variant. Another unique constraint on the old key would still prevent multiple sizes. Resolve ambiguous legacy lines with the owner. |
| Existing orders | Check duplicate payment/tracking references, invalid/missing totals, orphan owners, pending attempts per owner, recorded terminal statuses and existing finance writers. Map which gateway identifiers can be reconciled. Preserve the current basket for a historic snapshot missing row identity. |
| Auth and profiles | Confirm each usable account has its profile, anonymous sign-in is enabled, staff assignments are authorized and existing auth triggers cannot write conflicting roles. Verify redirect allowlists for confirmation and recovery against HTTPS staging. |
| Permissions | Inventory all table and column grants, RLS policies, function owners/EXECUTE, exposed schemas, inherited roles, sequences and other integrations. The October migration removes all policies on seven public tables and rebuilds grants; compare every displaced policy. Keep the private schema outside the Data API. Read policy for public reviews includes all granted columns, so review actual schema for personal fields. |
| Storage | Confirm product-image exists, reads work through the intended public/private access model, RLS is enabled for objects and restrictive guards coexist with other buckets. Exercise admin upload/update/delete, ordinary-user denial, configured MIME types and 5 MiB limit through Storage. |
| New database objects | Check private tables, views, triggers, functions, indexes and archive/variant/reference columns for name collisions, supported PostgreSQL version, privileges and lock times on representative volumes. Check archived orders remain visible to their owners. |

## Future cutover, subject to owner approval

1. Freeze new attempts in the active application, including legacy COD writes. Keep the correct callbacks available for already accepted attempts. Reconcile an inventory of outstanding orders against the merchant. Choose one active payment writer per reference and explicitly route any remaining old references to its owner.
2. Review historical exposure privately with the Resend and merchant administrators. Identify accounts and scopes without using old credentials. Coordinate replacements, verify on approved services, revoke old keys, inspect provider activity and retain confirmation privately. Merchant key changes may affect pending responses. An access code and merchant ID can be present in a legitimate gateway form; treat the working key separately. Control access to historical copies and Pages artifacts. History cleanup requires a separate plan and authorization.
3. Apply the reviewed migration sequence and deploy the staged artifact with new order creation disabled. Verify auth, catalog and read-only order access. Enable the verified callback handler for its assigned references before new online checkout. Test approved redacted monitoring and the support queue. Keep the old external backend and callback mapping until their in-flight obligations are reconciled.
4. After explicit approval, enable online initiation and, separately, both COD settings if approved. Observe receipt uniqueness, amounts, RLS denials, fulfilment transitions, queue age and failure rates. Verify balances with the merchant; a successful return page is insufficient.

## Rollback and reconciliation

Pause both new payment methods. Keep the correct existing callback writer and its committed receipts operating. Preserve logs and identifiers securely. Reconcile the full affected time window with the merchant and cash collector, including customers who never returned to the site. If application rollback is needed, restore only a compatible deployment. The legacy browser-writing application conflicts with the new RLS policies. Keep a maintenance storefront if no compatible writer is available. Prefer a reviewed forward repair; a database restore requires a separate recovery decision and replay plan for every later payment. Never mark a payment paid, release a fresh attempt or ask for another payment solely to clear a pending screen.
